# Устойчивая передача ручной сметы

`POST /api/estimates/upload` сохраняет прежние multipart-поля `file`, `title`
и принимает необязательное `operation_id` в формате UUID/32 hex. Браузер
сохраняет ключ до отправки в sessionStorage; он же без дефисов является job_id.
Без поля каждый POST по-прежнему считается отдельной новой загрузкой.

Ключ связывается с SHA-256 содержимого, безопасным именем файла и названием
сметы. Повтор даёт прежнее задание и `duplicate: true`. Другие байты, имя или
название с тем же ключом дают 409, не перезаписывая исходник. Повтор завершённого
задания не запускает парсер. После явного нового запуска из терминального
состояния браузер создаёт новый ключ. Если исходник принятого задания удалён,
повтор POST даёт 410 и не восстанавливает удалённые данные.

`upload_admission.py` использует существующие JSON-задания и блокировку ОС.
Под `data/user_estimates/.upload_jobs/admissions` сначала атомарно фиксируется
неизменяемая квитанция приёма. Файл пишется во временное имя внутри папки этой
операции, синхронизируется и переименовывается; затем фиксируется обычное задание.
Парсер запускается только после возврата из этой процедуры. Собственные
временные `.receiving-*.tmp` после гибели процесса удаляются под той же блокировкой;
чужие имена и символьные ссылки не затрагиваются. Новая БД/миграция не нужны.

Если процесс остановился после квитанции, но до файла, статус сообщает
`retry_upload: true`: нужно повторить передачу того же файла с тем же ключом.
После сохранения файла, но до JSON-задания, следующий статус восстанавливает
задание из квитанции и проверяет SHA-256. Повреждённая квитанция/существующее
задание не заменяется догадкой. После приёма парсер также проверяет ожидаемую
SHA-256 исходника. Общая блокировка выполнения парсера и атомарная публикация
сметы остаются прежними.

Ответ с `ok: true, accepted: true, job_id` подтверждает сохранённую передачу.
Состояние разбора читается через прежний `GET /api/estimates/upload-status/<id>`.
Даже при 503 запуска обработчика возвращаются `accepted: true` и job_id, если
файл с заданием уже сохранены. Потеря всего ответа не лишает нового клиента
возможности проверить заранее известный job_id. Поля `original_url` и
`original_filename` доступны для существующего допустимого исходника, включая
ошибку разбора. Маршрут `/estimates/uploads/<job_id>/original` проходит обычную
авторизацию префикса `/estimates`; файл ограничен своей папкой и скачивается
вложением с `private, no-store`/`nosniff`.

В каталоге загрузкой владеет `static/estimate_upload.js`, подключённый через
защищённый `/estimates/upload-client.js`. Массовый импорт и фильтр каталога
сохраняются. Повторный submit во время подтверждённой работы заблокирован;
после потери ответа можно повторить прежнюю операцию. При недоступном статусе
есть явная проверка и переход к другой смете, который не отменяет принятое
задание. Подробный журнал закрыт по умолчанию; ошибка не показывает 100% готовности,
приблизительный прогресс отмечен ≈. Состояние восстанавливается при обновлении
страницы в этой вкладке; закрытие всей сессии браузера не является хранением
истории загрузок. Старый sessionStorage job_id также читается.

Проверки: `test_upload_admission.py`, пять реальных процессных границ в
`test_upload_admission_processes.py`, исполняемый Node-набор
`estimate_upload_frontend_tests.js`, прежние тесты парсера/сохранения/массового
импорта. При релизе проверяется итоговый Linux-образ без сети и UI 390/768/1280.
Реальная полнота OCR/цен этими тестами не подтверждается.

незавершённую квитанцию и не читает новый ключ sessionStorage. Не удалять квитанции
во время очистки старого UI: они предотвращают повтор при поздней доставке запроса.
