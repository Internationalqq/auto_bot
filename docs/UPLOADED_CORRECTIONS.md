# Исправления загруженной сметы

У позиции в `/estimates/<id>` есть действие «Проверить строку». Рядом с текущими полями показаны первое распознавание и исходный файл. Можно уточнить название, шифр, тип, единицу, количество, цену и сумму. Причина обязательна; автор определяется действующей сессией PM.bi. Сумма переносится с учётом коэффициентов исходника: приложение не вычисляет её произвольно из количества и цены.

## Контракт

- GET `/estimates/<id>/review?position_id=...` открывает одну физическую строку.
- GET `/api/estimates/<id>/corrections` возвращает текущую версию и 20 последних изменений. `before` листает историю; `position_id` добавляет текущую и исходную строку.
- POST принимает ровно `position_id`, `changes`, `expected_version`, `operation_id`, `reason`. `changes` содержит только перечисленные поля. Клиент сохраняет UUID и тело до отправки.
- GET с `operation_id` восстанавливает подтверждение только для того же автора. Повтор POST с тем же содержимым возвращает прежнюю редакцию, в том числе после более поздних правок. Другие данные с тем же ключом и устаревшая версия дают 409.
- Деньги вводятся до двух знаков, количество — до шести; сохраняются десятичные строки и целые копейки. Пустое значение остаётся неизвестным. Ноль не заменяется запасным значением. Допустимы отрицательные числа из документа, но не некорректные закупочные позиции при импорте в CRM.
- Для исправленной позиции импорт требует явных единицы, положительного количества, неотрицательных цены и суммы. При неполных данных весь payload отвергается с 422. Идентификатор строки импорта основан на исходных координатах и не меняется из-за переименования.

## Данные и отказоустойчивость

Первоначальные meta/rows и файл не перезаписываются. `uploaded_estimates.load_document` возвращает согласованную текущую пару метаданных/строк. Неисправленные документы сохраняют прежний контракт. Карточка, каталог, XLSX, поиск и импорт CRM читают текущую редакцию. Исходник скачивается независимо от доступности истории.

При первом исправлении создаётся отдельная `.corrections.sqlite3` в каталоге загруженных смет. Единственная таблица `estimate_revisions` содержит уникальные номер редакции в документе, SHA версии и ключ операции. JSON события включает накопленные переопределения, изменения до/после, автора, причину, время UTC и SHA исходных строк. DDL и событие записываются одной транзакцией `BEGIN IMMEDIATE`, `synchronous=FULL`. Чтение БД не создаёт. Старые SQLite/JSON не мигрируют.

Перед новой правкой проверяются версия исходных строк и SHA файла, если она была записана при загрузке. Для старых документов без SHA действует контроль исходных строк. Порядок блокировок: блокировка источника, затем SQL исправлений. Запрещено брать write-lock очереди внутри блокировки источника. Завершённое сохранение и повторный запрос переживают перезапуск; сбой до commit оставляет прежнюю редакцию.

Изменяется `estimate_version` только исправленной строки. Её старые предложения, включая старый формат без версии, перестают сопоставляться. Неизменённые позиции сохраняют рынок. Уже взятое в работу или подготовленное задание со старым SHA не может опубликовать результат после исправления. Повторный поиск использует общую сохраняемую очередь.

## Доступ и исходник

`crm_actor` обращается к `/api/auth/me` на настроенном `PMBI_CRM_URL`, передавая только Cookie/Authorization текущего запроса. Роли: main_admin, admin, director, foreman. Автор из тела запрещён; сервисная учётная запись не используется. Перенаправления и прокси окружения отключены, запрос ограничен 8 секундами и 64 КиБ. Нет сессии — 401, запрещённая роль — 403, недоступна проверка — 503. Nginx сохраняет существующую защиту `/estimates` и `/api/estimates`.

Excel показывает ограниченную таблицу исходных ячеек. PDF рендерится по одной странице в существующем отдельном обработчике, без исполнения содержимого PDF в браузере. Стартовая страница берётся из исходных координат строки. Есть выбор страницы и масштаб. Лимиты: файл 128 МиБ, 250 страниц, одна картинка до 3 Мп и 8 МиБ, время 25 секунд, адресное пространство Linux 768 МиБ; Windows ограничен watchdog. Одновременный просмотр ограничен общей блокировкой. При отказе оригинал остаётся доступен. CSP допускает только свои стили и встроенное изображение.

## Проверка и выпуск

Проверки поведения: точные копейки, неизвестные значения, неизменность исходника, роли и подмена автора, устаревший рынок, стабильные ключи CRM, конфликт вкладок, потеря подтверждения, дубли, реальное завершение процессов до/после commit, следующий запрос и перезапуск, PDF/Excel. UI проверяется на изолированной БД при 390, 768, 1280 px. Пробные правки рабочих данных запрещены.

Резервная копия включает новую БД через SQLite backup с integrity/FK и контрольным восстановлением, а также исходники и текущий образ. **После появления пользовательских исправлений нельзя просто откатиться на старый код, который не читает историю:** он покажет первоначальное распознавание. Обычный откат на предыдущий образ допустим лишь при отсутствии записей исправлений. Иначе сохраняют всю историю и выпускают совместимое исправление либо отдельно готовят перенос текущих значений с сохранением аудита. Старую резервную БД нельзя накатывать поверх новых пользовательских действий.

Этот механизм относится к загруженным сметам. Проверка/исправления строк в документах тендера и приёмка распознавания на размеченной выборке остаются отдельными этапами. Исправление пользователем само по себе не подтверждает рыночную цену или прибыль.
