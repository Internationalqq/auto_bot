# Поиск и обработка документов: сохранённые задания

Принятый через веб-интерфейс поиск ЕИС, повторное скачивание, разбор одного тендера или массовая пересборка сначала записывается в `data/main_jobs.sqlite3`. Ответ содержит `run_id`. Снимок аргументов, фильтров или списка тендеров фиксируется при приёме; команда оболочки и произвольный модуль из HTTP не принимаются.

## Выполнение и восстановление

- Одно активное задание (`queued` или `running`) на хранилище. SQLite проверяет это между процессами; другой запуск получает прежний HTTP 409.
- Старые действия сравнения и удаления тендера тоже проверяют сохранённое задание, включая открытие в новом web-процессе. Если хранилище недоступно, эти действия блокируются до восстановления чтения.
- Отдельный процесс `autobot.main_job_runtime` получает блокировку исполнения ОС, переводит запись в `running` и вызывает существующий CLI. Его время жизни и потоки вывода не зависят от web-процесса.
- При остановке только web-процесса исполнитель продолжает работу. После старта новый web-процесс видит его сохранённое состояние.
- При старте приложения ещё не начатый `queued` запускается. Если `running` больше не держит блокировку ОС, он становится `interrupted`. По времени последнего сообщения прерывание не определяется.
- Прерванное задание **автоматически не повторяется**. CLI мог успеть сохранить отчёт или отправить существующее уведомление до остановки. Пользователь проверяет файлы и явно повторяет нужное действие. Завершённые результаты не меняются при повторном восстановлении.
- Завершение CLI с ненулевым кодом — `failed`; исходный код сохраняется. Массовый разбор сохраняет порядок принятого списка, продолжает после ошибки отдельного тендера и показывает число обработанных тендеров.

Блокировка исполнения принадлежит процессу задания. Восстановление публикации набора отчётов остаётся отдельным механизмом, описанным в `DOCUMENT_PARSING.md`. Состояние задания не выдаёт неподтверждённую публикацию за успешный результат.

## API и интерфейс

Существующие URL и коды успешных ответов сохранены. Для защиты повтора клиент может передать `operation_id`: UUID с дефисами или 32 строчных шестнадцатеричных символа. Повтор с теми же условиями возвращает прежний `run_id` и `duplicate: true`, включая уже завершённый запуск; другие условия с тем же ключом дают 409.

`GET /api/parse-status` возвращает последний запуск и прежние сведения о документах/поиске. `run_id` выбирает конкретное сохранённое задание (400 при неверном номере, 404 при отсутствии); `tender_id` позволяет карточке найти последний запуск для данного тендера. Добавлены `job_status`, `done`, `total`. План, его контрольная сумма и аргументы CLI в ответ не выдаются.

Карточка повторно подключается к выполняющемуся заданию после открытия. Статус и свёрнутый журнал загрузки/разбора расположены рядом с основным действием. Текст журнала отображается как текст, без исполнения HTML. При потере ответа карточка и каталог сохраняют номер операции для повтора текущего действия; после перезагрузки страницу связывает с работой серверное состояние. Автоматического повторного POST при открытии нет.

Журнал ограничен последними 300 строками по 1500 символов, API отдаёт последние 80. Перехватывается вывод Python; прямые записи нативных библиотек в fd 1/2 уходят в `DEVNULL`, чтобы закрытие web-процесса не оборвало CLI. Это не полный архив диагностических сообщений.

## Эксплуатация и границы

Хранилище создаётся лениво, данные прежних тендеров не мигрируют. Добавьте его и SQLite WAL в действующий порядок резервного копирования. Перед обновлением или откатом дождитесь отсутствия активных заданий. При откате сохраните новый файл: прежний код его не использует. Не удаляйте и не редактируйте запись, чтобы «разблокировать» продолжающийся процесс.

В этой версии нет расписания, приоритетов, автоматического повтора прерванного CLI, очистки истории или одновременного выполнения нескольких основных заданий. Старый объединённый сценарий сравнения рынка сохраняет собственное состояние; поэтому один Gunicorn web-процесс остаётся настройкой по умолчанию. Серверный поиск рыночных цен использует отдельную очередь. Реальная доступность ЕИС и внешнего исполнителя Avito этой проверкой не подтверждается.

## Проверки

`tests/test_main_jobs.py`, `test_main_jobs_api.py`, `test_main_job_processes.py`: конкурентный приём, ключ повторного запроса, неизменность снимка, ограниченные журналы, старые URL, точный статус, отказ хранилища и запуска, потеря web-процесса/исполнителя, следующий процесс и состояние после сохранения результата. Процессные проверки используют настоящий runtime и блокировки ОС, но подменяют операцию CLI локальным стендом, без ЕИС и уведомлений.

`node tests/document_jobs_frontend_tests.js` и `node tests/catalogue_jobs_frontend_tests.js`: потерянный ответ, повтор, конфликт, другой тип действия, восстановление карточки, прерывание, отсутствие запуска, безопасный текст журнала и задержка опроса при сетевой ошибке.
