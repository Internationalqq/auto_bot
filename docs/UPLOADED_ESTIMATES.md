# Сохранение загруженных смет

Новые ручные загрузки записывают метаданные, строки и участие в каталоге одной транзакцией SQLite в `data/user_estimates/estimates.sqlite3`. Используется стандартная библиотека Python, `BEGIN IMMEDIATE`, `synchronous=FULL` и обычный rollback journal. Сбой до commit оставляет прежние записи; после commit вся новая смета уже доступна. Отдельного изменяемого индекса для новых записей нет. Чтение не создаёт базу и схему; первые записи создают их в той же транзакции. Повреждённое хранилище даёт 503 вместо ложного пустого каталога.

Оригинальный файл остаётся в прежней папке `<estimate_id>`. Существующие `index.json`, `meta.json` и `rows.json` продолжают читаться без переноса данных. Каталог объединяет новые записи и прежний индекс. Внутренний формат будущих загрузок изменён явно: новые `meta.json` и `rows.json` не создаются. Помощники web UI, карточка, сравнение, выгрузки и подготовка импорта CRM читают оба формата; URL и API сохраняются. Повтор публикации того же ID/источника/строк идемпотентен, другая версия под тем же ID отклоняется. Обновление метаданных рынка не может менять исходную сумму или источник.

Задание загрузки сначала сохраняется в `.upload_jobs/<job_id>.json`, затем запускается обработчик. Ошибка записи при приёме возвращает 503 и не запускает разбор; исходник сохраняется. JSON прогресса записывается через уникальный временный файл и атомарную замену, на Linux выполняется fsync файла и каталога. Чтение ограничено 64 КиБ. В памяти остаются все выполняющиеся загрузки и последние завершённые.

Выполнение одного задания и запись его конечной ошибки защищены существующей блокировкой ОС `.upload_jobs/<job_id>.run.lock`. Второй процесс наблюдения перечитывает сохранённый прогресс и не получает право второго выполнения. Проверка источника ограничивает его папкой целевой сметы. Повторное открытие `/api/estimates/upload-status/<job_id>` может возобновить прерванную обработку. Проверенная запись в SQLite восстанавливает «Готово» без повторного парсера; три прерванные попытки без результата останавливают автоматическое восстановление. Если исходник уже сохранённой сметы изменился, нужен отдельный новый файл/новая загрузка.

Ограничения: восстановление начинается при следующем обращении к статусу, отдельного расписания нет. Отдельный новый POST загрузки по-прежнему создаёт новую смету; защита повторного HTTP-приёма при потере первого ответа ещё относится к интерфейсу загрузки. Блокировка принадлежит web-исполнителю. После его гибели оставшийся дочерний парсер не может публиковать результат и ограничен ранее внедрённым watchdog; новый исполнитель может начать повтор локального разбора. Ограничения всех парсеров — в `DOCUMENT_PARSING.md`. Ресурсные данные, полное качество OCR и интерфейс ручных исправлений не становятся принятыми от изменения хранилища.

## Проверки и откат

Процессные проверки действительно завершают исполнителя до и после commit, между commit и записью статуса, при выполняющемся разборе; проверяют два независимых сохранения, двух исполнителей одного задания и повтор без нового разбора. В этих тестах парсер заменён локальной операцией; настоящий ограниченный Excel/PDF-процесс проверяется отдельно. Исчезновение питания не эмулируется; на Windows используемый API не даёт fsync каталога для файлов прогресса.

При выпуске существующие рабочие данные не мигрируют. Резервное копирование должно включать новую SQLite-базу стандартным SQLite backup API и всю папку исходников. Возврат к образу до этого формата безопасен напрямую только пока новых SQLite-записей нет. Старый образ не читает новую базу; нельзя откатывать его вслепую или восстанавливать старый backup поверх новых загрузок.

Для отката после новых загрузок сначала остановить приём/обработку, сделать свежую проверенную резервную копию и создать отдельный артефакт:

```text
python tools/export_uploaded_estimates.py /path/to/user_estimates /new/private/rollback-artifact
```

Команда читает согласованный снимок новых записей и прежний индекс, создаёт прежние `meta.json`, `rows.json` и объединённый `index.json` в новом каталоге вне рабочих данных. Оригиналы и результаты рынка остаются в исходной папке, рабочая база и файлы не меняются. Каталог назначения должен отсутствовать. После проверки количества, SHA исходников, строк и чтения старым кодом применяется отдельный план переноса: добавить только проверенные новые JSON в их существующие папки, сохранить все прежние записи и резервную копию индекса, заменить индекс, затем запускать старый образ. Эта команда сама не выполняет перенос в production. Предпочтителен откат на проверенный образ, который уже поддерживает оба формата, если такой образ доступен.
