# Поставщик → запрос → ответ → цена

Baseline AutoBot f1b2cb8, CRM c8be388. Чужой checkpoint и untracked сохранены.
Результат: скрипт группирует выбранные позиции по подтверждённому ассортименту
поставщика вне границ разделов; один запрос/канал, серверная история, ответ и
цены по строкам. Агент видит только предмет запроса и свою переписку.

Порядок: реестр/группировка → отправка → очередь проверки ответов → связанные
предложения в интерфейсе → изолированные тесты/визуальная проверка → выпуск
с резервом → первые реальные обращения. Сохраняем старые API/черновики,
финансовые поля, ACL, защиту неопределённых отправок. Мессенджер доступен
только после фактической проверки канала; телефон не означает WhatsApp/MAX.

План данных: новые таблицы переписки и цен в отдельной buyer_outbox SQLite,
без переписывания смет и старых журналов. Перед production резерв SQLite и
образ для отката. Новые столбцы предложений показывают сохранённые ответы,
не меняют экономику до проверки сопоставимости. Ошибки канала не дают sent.

Проверки: группировка через разделы, несколько направлений, чужой тендер,
повтор/перезапуск, дубли ответа, чужой отправитель, единица/НДС/цитата/цена,
частичный ответ, права API, UI 390/768/1280. Живые сообщения только реальным
поставщикам по утверждённому назначению, без вложений и цены сметы.

Реализация: buyer_suppliers формирует готовое обращение скриптом из разрешённых
полей; реестр 6 публичных поставщиков Ярославской области, ассортиментные правила
для щебня/песка/грунта/кабеля/электрики/освещения/знаков. Каждое отправление
повторно проверяет опубликованный контакт. Это ограниченный проверяемый реестр,
не универсальный поиск любых регионов. Один supplier-job содержит строки из
разных разделов. Неизвестные категории/подрядчики и отрицательные количества
не теряются — отображаются как непокрытые с причиной.

buyer_replies хранит исходное сообщение и извлечённые цены. У каждого ответа
известен исходящий запрос; чужой sender, неизвестная строка, отсутствующая
цитата и изменение уже известного сообщения отклоняются транзакционно.
Отсутствие ответа не создаёт цену. Явные метрические коэффициенты переводятся
скриптом, упаковки не угадываются. Смета/рыночная медиана/экономика не
перезаписываются; «Ответ поставщика» показан рядом в позиции и переписке.
Сравнимость ответа не означает включённую доставку или чистую прибыль.
Mac-исполнитель читает только ответы на sent-запросы; никаких автоответов,
оплат, заказов и вложений. Проверки идут отдельно от отправки.

Проверки до выпуска: 87 unittest (29 Hermes, 9 jobs, 14 outbox, 6 campaigns,
10 market_queue, 19 workflow) PASS, 17 pytest tender detail/filter/economics
PASS, buyer_frontend и tender_workspace_frontend PASS. Первые запускались
неподходящим Python без requests; повтор штатным py -3.11 успешен. Три pytest
модуля первоначально дали 0 unittest, поэтому отдельно реально запущены pytest.
Полный suite не запускался. UI 390/768/1280: overflow=false, текст запроса
свёрнут, ответ/условия/цена и статус читаются. Снимки .impeccable/review/buyer-workflow
явно содержат тестовые данные, не доказательство реальной отправки.
Детектор один раз: прежнее предупреждение из-за неразрешённых Jinja CSS.

Финальное ревью: ship после устранения трёх замечаний и проверки регрессий.
Изменённые характеристики позиции или регион больше не допускают старую цену
в связанные предложения: сравнивается снимок предмета запроса с текущей
позицией и регионом. Ответ остаётся в истории переписки. Редактирование текста
исходящего запроса делает привязку строк недоверенной (mapping_trusted=false):
извлечённая цена получает review с объяснением и не привязывается автоматически
к смете. Сохранение непокрытых позиций восстановлено после GET и повторного
открытия страницы; эти три сценария покрыты workflow-проверками.

Новая таблица buyer_supplier_plans в БД очереди хранит последний результат
подготовки отдельно по tender_id: result_json и updated_at. Запись результата
и создание заданий выполняются в одной транзакции. GET возвращает coverage,
интерфейс восстанавливает число покрытых позиций и список непокрытых с причинами.
Это снимок последней подготовки, а не обещание актуального полного покрытия.

Дизайн остаётся расширением действующего Operate. PRODUCT.md подтверждает
компактные таблицы, спокойные поверхности, исходные токены/шрифт и одну главную
кнопку на блок. Его ограничение «без отправки» относится к первому пакету
каталога; текущий сценарий переписки описан в этом отчёте. Источники визуальных
правил — autobot/static/autobot-ui.css и tender_detail.css; buyer.css использует
существующие --line, --muted, --blue, --text, --surface и наследуемый шрифт.
Общий поставщик раскрывается в одну группу поверх разделов; внутри явно
различаются адресат, канал, статус, точный текст запроса, ответ и цены/условия.
На узком экране статус и поля переносятся, длинные названия остаются читаемыми.
Просмотрены три снимка в .impeccable/review/buyer-workflow: это демонстрация
на изолированной копии с явной подписью об отсутствии реальной отправки.
PRODUCT.md и действующие файлы системы не менялись в этапе документирования;
новые DESIGN.md, design.json и выдуманные токены не создавались.

На копии все 35 подходящих материальных строк дали 34 покрытых реестром и
5 запросов; одна отрицательная корректировка пропущена. Нажатие основного
действия без выбора берёт только строки без подтверждённой цены: 31 в запросах,
177 без подходящего источника (не обещаем полное покрытие).

Проверка контактов с ПК: пять из шести доступны, Технолайт дал timeout;

CRM после перезапуска почтового API и read-only проверки интерфейса. Новый
run_c4161d3f9edb40d9aa20c3f3b61032e2: blocked, рабочий ящик подтверждён,
«Отправленные» пусты, same_pid_keyboard_ambiguity, set_value не заполнил текст.

прошли в кандидатном Linux-образе, health и запрет неавторизованных API прошли.

образа для отката. Пересоздан только AutoBot; CRM, nginx и хеши отчётов сохранены.

резерв connector/before-workflow-20260926T080005Z, перезапущен buyer-sender.

В production нажатием основной кнопки подготовлены 5 обращений на 25 уникальных
